# Genetic Algorithm Itinerary Optimizer

## 1. Problem Statement

The optimization problem is a multi-day tourist itinerary routing problem. The
input itinerary is generated by an LLM and grouped by day and part of day:
Morning, Afternoon, and Evening.

The goal is to reorder and redistribute all selected points of interest (POIs)
across the available trip days while:

- minimizing travel time
- minimizing travel distance
- keeping each day inside a daily time budget
- respecting opening hours when raw POI data is available
- keeping days reasonably balanced
- ensuring every POI is visited exactly once

Each day starts and ends at the hotel. This makes the problem similar to a
multi-day Traveling Salesman Problem (TSP) or Vehicle Routing Problem (VRP),
where each day acts like one route.

## 2. Why Genetic Algorithm

This problem is combinatorial. Even a modest itinerary can have a very large
number of possible POI orders and day assignments. Exact solvers such as
OR-Tools are powerful, but a Genetic Algorithm (GA) is useful for this project
because it is easy to explain, flexible, and can combine several soft
constraints in one fitness function.

The GA searches the solution space using an evolutionary process:

1. Generate many candidate itineraries.
2. Score each candidate using a fitness function.
3. Select stronger candidates as parents.
4. Create new candidates using crossover and mutation.
5. Repair invalid candidates.
6. Repeat until the solution improves or early stopping is reached.

GA does not guarantee the global optimum, but it can find strong practical
solutions and gives useful convergence metrics for analysis.

## 3. Chromosome Representation

The optimizer uses a route-based chromosome. Each chromosome is a list of daily
routes, and each daily route is a list of 0-based POI indices.

```text
Chromosome = [
  Day1 route: [POI3, POI1, POI5],
  Day2 route: [POI0, POI4],
  Day3 route: [POI2, POI6, POI7]
]
```

Example:

```python
routes = [
    [3, 1, 5],
    [0, 4],
    [2, 6, 7],
]
```

This means:

- Day 1 visits POI 3, then POI 1, then POI 5.
- Day 2 visits POI 0, then POI 4.
- Day 3 visits POI 2, then POI 6, then POI 7.

Internally, POIs are 0-based. In the distance and time matrices, node 0 is the
hotel, so POI `i` is matrix node `i + 1`.

The chromosome representation directly matches the final itinerary output,
which makes decoding simple.

## 4. Fitness Function

The GA uses a minimization cost, then converts it to maximization fitness:

```text
cost =
  travel_time_weight * total_route_time
+ distance_weight * total_distance
+ over_budget_weight * over_budget_penalty
+ opening_hours_weight * opening_hours_penalty
+ balance_weight * balance_penalty
+ empty_day_weight * empty_day_penalty

fitness = 1 / (1 + cost)
```

Default weights:

```python
DEFAULT_WEIGHTS = {
    "travel_time": 1.0,
    "travel_distance": 0.001,
    "over_budget": 10_000.0,
    "opening_hours": 5_000.0,
    "balance": 2.0,
    "empty_day": 20_000.0,
}
```

Fitness components:

- Route time: total driving time plus inferred POI visit duration in minutes.
- Travel time: reported separately as total driving time in minutes.
- Travel distance: total driving distance from the matrix.
- Visit duration: inferred from raw POI data and included in route time.
- Over-budget penalty: minutes above the daily time budget.
- Opening-hours penalty: count of visits that arrive while the POI is closed.
- Balance penalty: standard deviation of daily route times.
- Empty-day penalty: count of days with zero POIs.

The distance and time matrices are built once before the GA loop. The fitness
function never calls Geoapify, which keeps evaluation fast.

## 5. Genetic Operators

### Tournament Selection

Tournament selection randomly samples a small group of chromosomes and selects
the one with the best fitness. This gives good chromosomes a higher chance of
being selected without removing diversity too quickly.

### Ordered Crossover

The route-aware crossover works in two stages:

1. Flatten both parent chromosomes into POI permutations.
2. Apply ordered crossover (OX) to create a child permutation.
3. Split the permutation back into daily routes using a mixture of parent route
   lengths.

Ordered crossover preserves relative POI order from both parents and avoids
duplicating POIs when parents are valid.

### Mutation

The mutation function randomly applies one of four local changes:

- swap two POIs inside the same route
- move one POI from one day to another
- reverse a segment inside one route
- swap POIs between two different days

These mutations help the GA explore both ordering changes and day-assignment
changes.

### Repair Function

Repair is applied after crossover and mutation. It guarantees:

- every POI appears exactly once
- duplicate POIs are removed
- missing POIs are inserted
- invalid POI indices are removed
- the number of routes equals the number of days

This is important because GA operators can accidentally create invalid
solutions.

## 6. Evolutionary Loop

The GA loop follows this sequence:

```text
initial population
-> evaluate fitness
-> sort by fitness
-> keep elites
-> select parents
-> crossover
-> mutate
-> repair
-> evaluate children
-> replace population
-> repeat
```

The implementation tracks:

- best cost per generation
- average cost per generation
- best fitness per generation
- average fitness per generation
- best generation
- convergence generation
- runtime
- feasibility flag

Early stopping is supported with `early_stopping_patience`. If the best solution
does not improve for the configured number of generations, the loop stops.

## 7. Testing and Validation

Recommended validation steps:

- Test chromosome repair with duplicates, invalid POIs, and missing POIs.
- Test that over-budget routes receive worse cost than feasible routes.
- Test mutation and crossover outputs to confirm each POI appears once.
- Compare the GA result against the original LLM itinerary baseline.
- Run multiple random seeds and report best, average, and worst results.
- Plot the convergence curve using `plot_evolution_history`.
- Compare with OR-Tools using `compare_ga_with_ortools` when a VRP result is
  available.

The included unit tests use synthetic matrices so they do not call Geoapify.

## 8. User Manual

Run the optimizer from the V3 folder:

```bash
python ga_experiments.py --itinerary itinerary.json --hotel-lat 36.1147 --hotel-lon -115.1728 --raw-poi-files ../../data/raw/las_vegas/attractions.json ../../data/raw/las_vegas/restaurants.json --population-size 80 --generations 200 --mutation-rate 0.2
```

The runner:

1. Loads the itinerary JSON.
2. Runs `solve_multi_day_ga`.
3. Saves the result to `ga_results.json`.
4. Saves plots when matplotlib is available.
5. Prints the optimized daily summaries.

Notebook usage:

```python
from ga_experiments import run_experiment

result = run_experiment(
    itinerary_path="itinerary.json",
    hotel_lat=36.1147,
    hotel_lon=-115.1728,
    population_size=80,
    generations=200,
    mutation_rate=0.2,
    random_seed=42,
)
```

Main public function:

```python
from ga_optimizer import solve_multi_day_ga

result_json = solve_multi_day_ga(
    itinerary=itinerary,
    hotel_lat=36.1147,
    hotel_lon=-115.1728,
    daily_time_budget_hours=8,
    population_size=80,
    generations=200,
    random_seed=42,
)
```

## 9. Limitations

- GA does not guarantee the global optimum.
- Results depend on population size, mutation rate, crossover rate, and random
  seed.
- Opening hours are handled as penalties instead of hard constraints.
- The current implementation assumes every POI must be visited.
- For larger itineraries, runtime increases because many chromosomes must be
  evaluated.
- Geoapify is still required once per optimization run to build the initial
  matrices.

## 10. Future Improvements

- Add an elitist island model to preserve diversity across subpopulations.
- Add local search after mutation for route-level improvement.
- Add POI dropping for infeasible cases.
- Add stricter restaurant time-window constraints for breakfast, lunch, and
  dinner.
- Add user preference scoring for POI quality and personalization.
- Cache Geoapify matrices by POI set to avoid repeated API calls.
